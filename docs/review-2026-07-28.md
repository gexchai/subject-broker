## Verdict

The spike does what it was asked to do. The documentation collapsed from 71 files (59 of them
placeholders) to 6 written documents, the five-state governance machine is gone, and the
security claims are now backed by executable attack tests rather than prose.

The original review observations are useful, but several conclusions were too strong. In
particular, its proposed fix for F-01 would remove a tested security property, F-02 conflates
read auditing with auditing every MCP tool invocation, and F-03 assumes unrestricted shell
access after the threat model has explicitly excluded that access path from the broker's
guarantees.

The remaining work is better described as:

- **Two material operability or diagnostic gaps** (F-01, F-04).
- **Three documentation-contract clarifications** (F-02, F-03, F-05).
- **Four low-priority cleanup or hardening items** (F-06 through F-09).

None of these findings invalidates the spike's narrow claim: policy enforcement and
fail-closed auditing for `read_resource` calls made through the already-started MCP process.

## Disposition of the feedback

| Finding | Disposition | Why |
| --- | --- | --- |
| F-01 | Accept the observation; reject the proposed fix | Ordinary atomic saves change inode, but accepting any new inode per read would defeat the tested replacement check. The product must choose mutable or session-pinned resources explicitly. |
| F-02 | Partly accept | ADR-006 is ambiguous. The code consistently audits read outcomes, not all tools. An empty successful list is not a denial and does not need a new reason code. |
| F-03 | Downgrade to clarification | A same-user agent with unrestricted shell can start another broker, but it can also read the file directly; that path is already explicitly out of scope. |

| F-06–F-08 | Accept | These are bounded cleanup/test-quality improvements. |
| F-09 | Accept as hardening, not a demonstrated vulnerability | Size and encoding behavior should be explicit before production use; the trusted owner currently controls registration. |

## Findings

### F-01 — Medium — Session-pinned file identity makes normal atomic saves unavailable

`ResourceRegistry.create` captures `dev`+`ino` once at startup (`src/resource-registry.ts:96`)
and `openVerified` rejects any mismatch (`src/resource-registry.ts:131-137`). Almost every
editor saves by writing a temporary file and renaming over the target, which always changes the
inode.

Observed:

```
1a read before edit   : allow    ALLOWED            content returned
1b read after  edit   : error    RESOURCE_CHANGED   ← after one ordinary editor save
1c read after restart : allow    ALLOWED            content returned
```

So a project owner who atomically replaces a protected resource makes that resource unavailable
for the remainder of the process lifetime, and the only signal is a reason code that means
"identity changed". This is not necessarily a security defect: the mechanism intentionally
treats every replacement as untrusted because it cannot infer whether the replacement was an
authorized save or an attack. It is, however, an undocumented and likely surprising lifecycle
constraint.

`QUESTIONS.md:34` tracks in-place mutation as open but does not cover rename-replace, which is
the far more common case.

**Recommendation.** Do not simply re-derive identity on every read: that would accept the exact
rename-replacement used by `tests/security/toctou.test.ts` and erase the guarantee recorded in
ADR-004. Choose and document one of these semantics:

1. For the spike, declare registered resources immutable for the life of the short-lived server
   and require restart after an owner update. Improve `RESOURCE_CHANGED` guidance so this is
   diagnosable.
2. If live updates are a real requirement, add an explicit trusted reload/re-registration
   operation that establishes a new identity. Define who may invoke it and how that authority is
   separated from the agent before implementing it.

Content hashes may help identify versions, but an automatically refreshed hash has the same
authorization problem as an automatically refreshed inode.

### F-02 — Medium — ADR-006 is ambiguous about whether non-read tools are audited

ADR-006 states: "Append one metadata-only JSONL event for **every** allow, deny, or error."
`ContextGuardBroker.explain` (`src/broker.ts:117-131`) and `listResources`
(`src/broker.ts:100-115`) return decisions without calling `#appendAudit`. The implementation
therefore conflicts with a literal reading of that sentence.

Observed against a fresh audit file:

```
2a explain(secret)         : deny / ACCESS_DENIED
2b explain(does-not-exist) : deny / ACCESS_DENIED
2c list                    : {resources: [], reasonCode: "ALLOWED"}
2d audit file size         : 0 bytes
```

The rest of ADR-006 is narrower: its title is "Audit failure blocks reads", its rationale is that
"every released read has an audit event", and the audit schema has only the `read` action.
Under that reading, the implementation and the central guarantee are aligned. Listing is
explicitly intended to reveal readable identifiers, and `explain_decision` intentionally reveals
whether a supplied identifier/action is allowed. Whether probes of those tools need an audit
trail is an operational requirement not yet established by the spike.

There is no secondary reason-code defect. `list_resources` successfully evaluated the policy and
returned an empty collection, so `ALLOWED` describes the operation correctly. "Nothing visible"
is data, not a denial.

**Recommendation.** Resolve the contract rather than assuming the broader one:

- If ADR-006 means read outcomes only, change "every allow, deny, or error" to "every
  `read_resource` allow, deny, or error" and add a test that each read attempt appends exactly one
  event.
- If audit consumers require every tool invocation, expand `AuditEvent.action`, make the broker
  methods asynchronous, define audit-failure behavior for non-content tools, and test all four
  tools. Do not add a special reason code for an empty successful list.

### F-03 — Low — Startup trust could be stated more explicitly

`THREAT_MODEL.md:18-26` puts a *confused or injected agent* in scope for attacks attempted
through the four MCP tools. The same document explicitly excludes an agent with unrestricted
shell or filesystem access and a malicious project owner controlling startup configuration.
A Claude Code deployment may grant shell access, but that is deployment-dependent and cannot be
assumed as an inherent capability of every injected-agent scenario.

Observed — same OS user, same policy file, self-selected subject and audit destination:

```
3  self-elevated read    : allow    content: "CANARY-SECRET-XYZ v2\n"
3b owner audit log       : unchanged — the read left no record there
```

The probe is valid but does not establish a contradiction. Once an attacker has same-user shell
access, it can already read the `0700` storage directly, alter policy and audit files, or launch
another process. The threat model and capability report already disclose the direct shell path,
identify owner-controlled startup as an assumption, and scope coverage to "this MCP process".

**Recommendation.** Add one sentence to the threat model or `uncoveredPaths` for readers who may
miss the implication: a same-user process can select different startup arguments and audit
destinations, so subject binding and audit completeness apply only to the owner-configured
ContextGuard process. This can amend ADR-011 or its supporting text; a new ADR is unnecessary
unless the trust boundary itself changes.

### F-04 — Medium — Configuration failure degrades silently to global deny and is undiagnosable

`loadPolicyAndRegistry` swallows every error and returns `undefined` (`src/broker.ts:57-59`).
The broker then starts successfully and denies every request with `POLICY_UNAVAILABLE`.
`server.ts:47-50` reduces startup failures to one generic stderr line.

This was found when the first probe run denied everything because `/tmp` resolves through a
symlink on macOS and `assertNoSymlink` (`src/resource-registry.ts:32-43`) rejects any symlinked
ancestor. Diagnosing that required reading the source, because a YAML typo, a wrong directory
mode, a symlinked ancestor, and a missing file are all indistinguishable at runtime.

Common macOS aliases such as `/tmp` make the constraint easy to encounter in development.
"Policy is misconfigured" and "storage identity is unacceptable" are also operationally
different events that currently share one external code. The existing behavior is fail-closed
and is explicitly tested, so it should not be described as a security failure.

**Recommendation.** Keep the broker's non-sensitive external response, but make server startup
validation fail with a structured diagnostic category such as `POLICY_PARSE_ERROR`,
`STORAGE_MODE_INVALID`, `PATH_CONTAINS_SYMLINK`, or `RESOURCE_MISSING`. Decide separately
whether the programmatic broker API should preserve its current deny-only mode for tests or
return a typed load result.

Do not relax the ancestor-symlink rule as part of this fix. "Resolve the real path and check
containment" has its own race and mount semantics and would supersede ADR-004. If support for
symlinked ancestors is required, specify the accepted filesystem model and add adversarial tests
before changing that rule.

### F-05 — Low — A real Claude Code run is not retained as evidence

`fixtures/claude-code/project/` contains no retained `contextguard-audit.jsonl`, transcript, or
captured `capability_report` from a real Claude Code session. The absence of an ignored local
file does not prove that no run occurred, but it does mean the repository cannot substantiate
one.

`.mcp.json` and `contextguard.yaml` are intentionally gitignored generated state. This does not
make the setup irreproducible: `docs/integration-claude-code.md` gives commands that generate the
policy and either the MCP configuration or its CLI equivalent. A path-independent generator
would improve convenience, not repair a broken reproduction path.

`ADR-010` cites `docs/integration-claude-code.md` as evidence, but a document is not an
execution. The `.mcp.json` `${VAR}` interpolation itself is correct — Claude Code does expand
environment variables — so the gap is the demonstration, not the instructions.

**Recommendation.** Keep the integration document's current "synthetic setup" status unless a
real run is part of the acceptance claim. If it is, run it once and retain a redacted
`capability_report`, representative audit events, Claude Code version, and date. A small setup
script is optional ergonomic follow-up.

### F-06 — Low — Stale build output shadows the current build

`dist/src/*.js` is a duplicate tree from a build made before `rootDir` was set, dated a day
earlier than `dist/*.js`. Untracked, so harmless to consumers, but it is a trap for anyone
running a file directly. Delete it and make `build` clean its output directory.

### F-07 — Low — The leakage test's strongest-looking assertion is inert

`tests/security/leakage.test.ts:40` asserts `expect(everyOutput).not.toContain("stack")` —
the literal string, not the general absence of a stack trace. It would catch a serialized
`stack` property but not all rendered stack formats. The canary assertion on the line above
carries the core confidentiality evidence. Replace or supplement it with an assertion on the
absence of stack-shaped content (for example, no `at <fn> (<file>:<line>)` frames and no
absolute repository paths).

### F-08 — Low — Dead branch in audit error handling

`src/broker.ts:199-202`: both branches of the `instanceof` check return `false`. Collapse to a
single `return false`.

### F-09 — Low — Resource size and encoding are unspecified

`src/broker.ts:154` reads the whole resource as a utf8 string with no size limit. A registered
binary file is decoded with replacement characters; a large file can consume substantial
memory. Because the trusted project owner controls registration, this is not a demonstrated
attacker-controlled vulnerability under the current threat model. Before production use, add a
configured maximum size (deny above it with a distinct reason code) and state explicitly that
resources are UTF-8 text, or define binary behavior.

## Recommended sequencing

1. F-02 and F-03 — tighten the written scope without changing behavior.
2. F-04 — make startup failure legible while preserving fail-closed external responses.
3. F-01 — decide immutable-per-process versus trusted live reload before changing code.
4. F-05 — retain end-to-end evidence only if ADR-010 is intended to claim a completed manual
   integration rather than a selected and documented integration target.
5. F-06 to F-09 — cleanup and hardening, batchable where appropriate.

F-04 should land with startup-level tests for each diagnostic category. F-01 needs tests only
after its lifecycle semantics are decided: either codify restart-after-save or test the trusted
reload boundary. F-02 needs audit-count tests matching whichever contract is selected. F-03 is
a wording clarification, not a code fix.

## Appendix A — Runtime probe

Run from a directory outside the repository. `/private/tmp` is used deliberately rather than
`/tmp` because of F-04.

```bash
mkdir -p /private/tmp/cgprobe/proj /private/tmp/cgprobe/store
chmod 700 /private/tmp/cgprobe/store
printf 'CANARY-SECRET-XYZ\n' > /private/tmp/cgprobe/store/secret.txt
chmod 600 /private/tmp/cgprobe/store/secret.txt
cat > /private/tmp/cgprobe/proj/policy.yaml <<'YAML'
version: 1
storageRoot: /private/tmp/cgprobe/store
subjects: [low, high]
resources:
  secret:
    path: /private/tmp/cgprobe/store/secret.txt
rules:
  - {subject: high, resource: secret, action: read, decision: allow}
  - {subject: low,  resource: secret, action: read, decision: deny}
YAML
```

```js
// /private/tmp/cgprobe/probe.mjs — set REPO to this repository's absolute path
const REPO = '<repo>/dist/';
const { ContextGuardBroker } = await import(REPO + 'broker.js');
const { writeFile, rename, readFile } = await import('node:fs/promises');
const P = '/private/tmp/cgprobe';
const mk = (s, audit = P + '/proj/audit.jsonl') =>
  ContextGuardBroker.create({ policyPath: P + '/proj/policy.yaml', subjectId: s,
    auditPath: audit, workingDirectory: P + '/proj' });

// F-01: an ordinary editor save (write temp + rename) invalidates the session
const b = await mk('high');
console.log('1a', JSON.stringify(await b.readResource('secret')));
await writeFile(P + '/store/.tmp', 'CANARY-SECRET-XYZ v2\n', { mode: 0o600 });
await rename(P + '/store/.tmp', P + '/store/secret.txt');
console.log('1b', JSON.stringify(await b.readResource('secret')));
console.log('1c', JSON.stringify(await (await mk('high')).readResource('secret')));

// F-02: probing the policy surface leaves no audit trail
await writeFile(P + '/proj/audit2.jsonl', '');
const b3 = await mk('low', P + '/proj/audit2.jsonl');
console.log('2a', JSON.stringify(b3.explain('secret', 'read')));
console.log('2b', JSON.stringify(b3.explain('does-not-exist', 'read')));
console.log('2c', JSON.stringify(b3.listResources()));
console.log('2d', (await readFile(P + '/proj/audit2.jsonl', 'utf8')).length, 'bytes');

// F-03: a same-user process selects its own subject and audit destination
const b4 = await mk('high', P + '/proj/attacker-audit.jsonl');
const r = await b4.readResource('secret');
console.log('3 ', r.decision, JSON.stringify(r.content));
console.log('3b', (await readFile(P + '/proj/audit.jsonl', 'utf8')).split('\n').filter(Boolean).length,
            'events in the owner log');
```

Delete `/private/tmp/cgprobe` afterwards. The F-01 and F-02 probes are useful regression tests
once their intended lifecycle and audit contracts are decided. The F-03 probe demonstrates an
already-excluded same-user shell capability and does not need to become a broker security test.
